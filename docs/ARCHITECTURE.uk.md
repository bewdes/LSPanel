# Архітектура

> 🇬🇧 English version: [ARCHITECTURE.md](ARCHITECTURE.md)

LS Panel — це десктопний застосунок на [Tauri 2](https://tauri.app/): фронтенд на React/TypeScript, що рендериться в нативному webview, і бекенд-процес на Rust, який виконує всю роботу з файловою системою, процесами, базами даних і контейнерами. Обидві сторони спілкуються виключно через міст команд Tauri `invoke()` та емітери подій — фронтенд ніколи не звертається до Docker, SQLite чи файлової системи напряму.

```
┌─────────────────────────────┐        invoke("command", args)        ┌───────────────────────────────┐
│  Фронтенд на React (src/)   │ ─────────────────────────────────────▶│   Бекенд на Rust (src-tauri/) │
│  features/*, components/ui  │◀───────────────────────────────────── │   *_commands.rs + модулі      │
└─────────────────────────────┘        події (progress, logs, ...)    └───────────────────────────────┘
                                                                                  │
                                                                                  ▼
                                                                 SQLite (rusqlite) · Docker/Podman · PTY
```

## Фронтенд (`src/`)

- **`app/`** — оболонка застосунку та композиція дашборду.
- **`features/*`** — одна тека на кожну предметну область (сайти, контейнери, бази даних, резервні копії, знімки, сертифікати, пошта, environment-files, файли, логи, livelink, налаштування). Кожна фіча володіє власним(и) компонентом(ами) сторінки та локальними компонентами.
- **`components/ui/`** — спільні UI-примітиви у стилі shadcn, побудовані на Tailwind CSS 4 та Radix/Base UI.
- **`i18n/`** — по одному файлу на кожну фічу, кожен експортує словник `{ en, uk }`. `i18n/index.ts` надає `pickLanguage(dict, uk)` для вибору активної мови; жодного динамічного завантаження перекладів немає, словники імпортуються статично.
- **`hooks/`, `lib/`** — спільні React-хуки та утиліти (форматування, нормалізація помилок, каталог версій для шаблонів проєктів тощо).

## Бекенд (`src-tauri/src/`)

Бекенд не має єдиної абстракції "сервера" — це плаский набір модулів, зареєстрованих як команди Tauri. Кожна предметна область зазвичай ділиться на:

- **модуль даних/логіки** (наприклад, `sites.rs`, `containers.rs`, `snapshots.rs`) зі звичайними функціями та (де)серіалізованими структурами, і
- модуль **`*_commands.rs`**, що обгортає цю логіку у функції з атрибутом `#[tauri::command]`, які фронтенд може викликати через `invoke()`.

`bootstrap.rs` — це композиційний корінь: він будує `tauri::Builder`, реєструє спільний стан у пам'яті, виконує налаштування при старті й перелічує кожну команду в єдиному виклику `tauri::generate_handler![...]` (~120 команд на момент написання).

### Спільний стан застосунку

Реєструється через `.manage(...)` у `bootstrap.rs` і передається в команди як `tauri::State`:

- `logs::LogStreams` — активні підписки на live-логи проєктів/контейнерів.
- `terminal::TerminalSessions` — відкриті PTY-сесії (на основі `portable-pty`) для вбудованого термінала.
- `native_runtime::NativeProcesses` — дочірні процеси / статичні файлові сервери, запущені для проєктів, що працюють **без** контейнера (див. нижче).

### Збереження даних

Усі стійкі дані живуть в одній базі SQLite в каталозі даних застосунку ОС (`<app_data_dir>/lspanel.sqlite3`), відкритій через `rusqlite` з журналюванням WAL. `storage.rs` володіє з'єднанням і системою міграцій на основі `PRAGMA user_version` (`migrate_schema_v1`, ...); таблиці включають `settings`, `environments`, `sites` та `operations`, зазвичай зберігаючи структуровані дані як JSON-колонки для гнучкості. Зовнішнього сервера бази даних немає — цей файл SQLite є власним сховищем метаданих LS Panel, окремим від будь-яких баз даних проєктів (Postgres/MySQL тощо), якими користується _керований проєкт_ — ними займаються `database.rs`/`database_commands.rs`.

### Середовища та runtime

**Сайт** (проєкт, яким керує LS Panel) працює всередині **середовища** (environment), яке може спиратися на один із двох runtime:

- **Контейнерний runtime** (`container_runtime.rs`, `container_lifecycle.rs`, `container_inspection.rs`, `container_logs.rs`, `container_routes.rs`, `container_validation.rs`) — автовизначає `docker` чи `podman` у `PATH` (налаштовується) і керує Compose (`docker compose` чи `podman-compose`) для підняття/зупинки стеків, інспекції сервісів і потокового читання логів.
- **Нативний runtime** (`native_runtime.rs`) — для типів проєктів, яким контейнер не потрібен (наприклад, простий статичний сайт чи легкий dev-сервер), LS Panel натомість напряму запускає дочірній процес або віддає файли вбудованим статичним сервером, відстежуючи це в `NativeProcesses`.

`project_templates.rs` розгортає нові сайти для конкретних стеків (наприклад, завантаження й налаштування WordPress, встановлення Laravel через Composer і підключення його `.env`), а також підтримує загальний імпорт/клонування/копіювання наявних проєктів, з механізмом захоплення/відкату `DirectoryBaseline`, щоб невдале розгортання можна було скасувати.

### Операційний центр

Довші дії (розгортання, операції з контейнерами, відновлення знімків тощо) відстежуються як записи `Operation` (`operations.rs`): кожен має id, опціональний `environment_id`, `kind`, `status`, `progress` (0–100), мітку `stage` та часові позначки, зберігається в SQLite і надсилається на фронтенд як подія через `tauri::Emitter`. Одночасно для одного середовища дозволена лише одна активна операція. При старті `operations::recover_interrupted` узгоджує будь-яку операцію, що лишилася в стані `running` з попередньої сесії (наприклад, після краху), щоб UI ніколи не показував застарілий стан "виконується".

### Робота з файлами, чутливими до безпеки

`security.rs` централізує запис у файлову систему для всього, що експортується за межі власного каталогу даних застосунку (експорт `.env`, експорт знімків, експорт логів): запис іде у тимчасовий сусідній файл і перейменовується на місце лише після успіху, наявні symlink за цільовим шляхом відхиляються, а секретні значення можуть бути замасковані в логах/виводі.

### Інші бекенд-модулі

- `tls.rs` / `certificate_commands.rs` — локальний центр сертифікації та випуск HTTPS-сертифікатів для окремих доменів.
- `mailpit.rs` / `mailpit_commands.rs` — звертається до локального інстансу [Mailpit](https://github.com/axllent/mailpit) для перегляду/читання/видалення/відправлення перехоплених листів.
- `git.rs` / `git_commands.rs` — Git-статус/дії для окремого сайту (ініціалізація, checkout, remote) для контролю версій проєкту.
- `diagnostics.rs` / `diagnose.rs` / `disk_usage.rs` — перевірки стану системи/середовища та звіт про використання диска, показані на сторінці "Стан системи".
- `terminal.rs` / `terminal_commands.rs` / `quick_commands.rs` — PTY-сесії термінала, а також збережені "швидкі команди" та історія команд для кожного сайту.
- `settings.rs` / `settings_commands.rs` — загальні налаштування панелі (мова, оформлення, типові значення проєкту).

## Збірка та інструменти

- **Фронтенд**: Vite 6 + TypeScript + React 19, Tailwind CSS 4. `npm run build` спочатку перевіряє типи, потім збирає; `npm run dev` запускає лише dev-сервер Vite.
- **Бекенд**: стандартний Cargo workspace у `src-tauri/`, зібраний через `tauri-build`; `npm run tauri` / `npm run tauri build` запускають повну збірку десктопного застосунку через Tauri CLI.
- **CI** (`.github/workflows/ci.yml`) виконує перевірки фронтенду (Prettier, ESLint, фронтенд-тести, `tsc`, збірка Vite), перевірки Rust (`cargo fmt --check`, `cargo clippy -D warnings`, `cargo test`), а потім збирає Linux-бандли `.deb`/`.rpm`/`.AppImage`.

Дивіться [FEATURES.uk.md](FEATURES.uk.md) для огляду кожної фічі та бекенд-команд, що її реалізують.
