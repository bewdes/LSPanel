# Архітектура

> 🇬🇧 English version: [ARCHITECTURE.md](ARCHITECTURE.md)

LS Panel — це десктопний застосунок на [Tauri 2](https://tauri.app/): фронтенд на React/TypeScript, що рендериться в нативному webview, і бекенд-процес на Rust, який виконує всю роботу з файловою системою, процесами, базами даних і контейнерами. Обидві сторони спілкуються виключно через міст команд Tauri `invoke()` та емітери подій — фронтенд ніколи не звертається до Docker, SQLite чи файлової системи напряму.

```
┌─────────────────────────────┐        invoke("command", args)        ┌───────────────────────────────┐
│  Фронтенд на React (src/)   │ ─────────────────────────────────────▶│   Бекенд на Rust (src-tauri/) │
│  features/*, components/ui  │◀───────────────────────────────────── │   *_commands.rs + модулі      │
└─────────────────────────────┘        події (progress, logs, ...)    └───────────────────────────────┘
                                                                                  │
                                                                                  ▼
                                                                 SQLite (rusqlite) · Docker/Podman · PTY
```

## Фронтенд (`src/`)

- **`app/`** — оболонка застосунку та композиція дашборду.
- **`features/*`** — одна тека на кожну предметну область (сайти, контейнери, бази даних, резервні копії, знімки, сертифікати, пошта, environment-files, файли, логи, livelink, налаштування). Кожна фіча володіє власним(и) компонентом(ами) сторінки та локальними компонентами.
- **`components/ui/`** — спільні UI-примітиви у стилі shadcn, побудовані на Tailwind CSS 4 та Radix/Base UI.
- **`i18n/`** — по одному файлу на кожну мову в `locales/` (`en.ts`, `uk.ts`), кожен експортує повний словник перекладу для цієї мови. `i18n/index.ts` надає `pickLanguage(language: string)` для вибору активної мови за кодом локалі (наприклад, `settings.language`), з відкатом на англійську; жодного динамічного завантаження перекладів немає, словники імпортуються статично.
- **`hooks/`, `lib/`** — спільні React-хуки та утиліти (форматування, нормалізація помилок, каталог версій для шаблонів проєктів тощо).

## Бекенд (`src-tauri/src/`)

Бекенд не має єдиної абстракції "сервера" — це плаский набір модулів, зареєстрованих як команди Tauri. Кожна предметна область зазвичай ділиться на:

- **модуль даних/логіки** (наприклад, `sites.rs`, `containers.rs`, `snapshots.rs`) зі звичайними функціями та (де)серіалізованими структурами, і
- модуль **`*_commands.rs`**, що обгортає цю логіку у функції з атрибутом `#[tauri::command]`, які фронтенд може викликати через `invoke()`.

`bootstrap.rs` — це композиційний корінь: він будує `tauri::Builder`, реєструє спільний стан у пам'яті, виконує налаштування при старті й перелічує кожну команду в єдиному виклику `tauri::generate_handler![...]` (~130 команд на момент написання).

### Спільний стан застосунку

Реєструється через `.manage(...)` у `bootstrap.rs` і передається в команди як `tauri::State`:

- `logs::LogStreams` — активні підписки на live-логи проєктів/контейнерів.
- `terminal::TerminalSessions` — відкриті PTY-сесії (на основі `portable-pty`) для вбудованого термінала.
- `native_runtime::NativeProcesses` — дочірні процеси / статичні файлові сервери, запущені для проєктів, що працюють **без** контейнера (див. нижче).
- `tunnel_provider::TunnelProcesses` — дочірні процеси, що обслуговують активний тунель LiveLink (ngrok/cloudflared).

### Збереження даних

Усі стійкі дані живуть в одній базі SQLite в каталозі даних застосунку ОС (`<app_data_dir>/lspanel.sqlite3`), відкритій через `rusqlite` з журналюванням WAL. `storage.rs` володіє з'єднанням і системою міграцій на основі `PRAGMA user_version` (`migrate_schema_v1`, `migrate_schema_v2`, ...), яка при кожному запуску повторно виконує всі ідемпотентні `CREATE TABLE IF NOT EXISTS`, а не покладається лише на рівність версії — тож частково застосована збірка не може лишити таблицю відсутньою назавжди; таблиці включають `settings`, `environments`, `sites`, `operations` та `notifications`, зазвичай зберігаючи структуровані дані як JSON-колонки для гнучкості. Зовнішнього сервера бази даних немає — цей файл SQLite є власним сховищем метаданих LS Panel, окремим від будь-яких баз даних проєктів (Postgres/MySQL тощо), якими користується _керований проєкт_ — ними займаються `database.rs`/`database_commands.rs`.

### Середовища та runtime

**Сайт** (проєкт, яким керує LS Panel) працює всередині **середовища** (environment), яке може спиратися на один із двох runtime:

- **Контейнерний runtime** — `containers.rs` є оркестратором CRUD/життєвого циклу/inspection; він делегує окремим сусіднім модулям, а не робить усе сам: `container_schema.rs` (структура `Environment` та її дефолти), `container_validation.rs` (уся валідація полів `Environment`), `container_compose.rs` (генерація шаблонів docker-compose/Dockerfile), `container_bootstrap.rs` (очікування готовності бази даних і створення за відсутності), `container_gateway.rs` (спільний nginx-шлюз: маршрутизація, підключення TLS, повтори при recreate після рестарту), `container_logs.rs` (потокове читання логів), `container_lifecycle.rs`, `container_inspection.rs`, `container_routes.rs` і `container_runtime.rs` (автовизначає `docker` чи `podman` у `PATH`, налаштовується, і відповідного постачальника Compose).
- **Нативний runtime** (`native_runtime.rs`) — для типів проєктів, яким контейнер не потрібен (наприклад, простий статичний сайт чи легкий dev-сервер), LS Panel натомість напряму запускає дочірній процес або віддає файли вбудованим статичним сервером, відстежуючи це в `NativeProcesses`.

`project_templates.rs` розгортає нові сайти для конкретних стеків (наприклад, завантаження й налаштування WordPress, встановлення Laravel через Composer і підключення його `.env`), а також підтримує загальний імпорт/клонування/копіювання наявних проєктів, з механізмом захоплення/відкату `DirectoryBaseline`, щоб невдале розгортання можна було скасувати.

### Операційний центр

Довші дії (розгортання, операції з контейнерами, відновлення знімків тощо) відстежуються як записи `Operation` (`operations.rs`): кожен має id, опціональний `environment_id`, `kind`, `status`, `progress` (0–100), мітку `stage` та часові позначки, зберігається в SQLite і надсилається на фронтенд як подія через `tauri::Emitter`. Одночасно для одного середовища дозволена лише одна активна операція. При старті `operations::recover_interrupted` узгоджує будь-яку операцію, що лишилася в стані `running` з попередньої сесії (наприклад, після краху), щоб UI ніколи не показував застарілий стан "виконується".

### Робота з файлами, чутливими до безпеки

`security.rs` централізує запис у файлову систему для всього, що експортується за межі власного каталогу даних застосунку (експорт `.env`, експорт знімків, експорт логів): запис іде у тимчасовий сусідній файл і перейменовується на місце лише після успіху, наявні symlink за цільовим шляхом відхиляються, а секретні значення можуть бути замасковані в логах/виводі.

### Довірча модель

Кожну команду Tauri в `src-tauri/src/` можна викликати напряму з renderer з довільними аргументами — сьогодні через devtools, а в принципі й через скомпрометований/XSS'нутий webview. Це властивість самої IPC-поверхні, а не баг конкретної команди, і це означає, що два класи "проблем" — прийнятний ризик, а не те, що закриває точковий фікс однієї команди:

- Команди, чий легітимний UX — "діяти над шляхом, який користувач обрав через нативний діалог ОС" (експорт/імпорт бази даних/знімка, імпорт `.env`), перевіряють лише, що батьківська директорія цілі існує і не є symlink, але не обмежують шлях коренем проєкту — на відміну від `file_manager.rs`, чия модель "перегляд у межах цього проєкту" таке обмеження підтримує. Додавання обмеження тут зламало б UX "експорт/імпорт будь-куди", заради якого ці команди існують.
- Налаштовувані команди термінала/браузера/редактора (`desktop_commands.rs`, `settings.rs`) — свідомий "запасний вихід" для запуску довільного локального бінарника; вони перевіряються лише на непорожність, без shell-парсингу (тож ін'єкція через метасимволи неможлива), і без жодного allowlist понад це.

Обидва експлуатуються лише за тієї ж передумови — скомпрометованого renderer, — що й виклик будь-якої іншої команди напряму, і задокументовані тут, а не "виправлені", щоб майбутній контрибʼютор не повернув обмеження шляху, очікуючи, що воно закриє те, чого закрити не може.

Окремо: версії залежностей у `Cargo.toml`/`package.json` пінуються лише на рівні мажорної версії (наприклад, `tauri "2"`, `react "^19"`), а інсталяційні скрипти в `dependency_install.rs` завантажують сторонні інсталятори через `curl | sh` (запускаються через `pkexec`, тобто від root) без перевірки контрольних сум — стандартна практика для таких інструментів, але варто періодично запускати `cargo audit`/`npm audit`, а не покладатися на ручний огляд.

### Інші бекенд-модулі

- `tls.rs` / `certificate_commands.rs` — локальний центр сертифікації та випуск HTTPS-сертифікатів для окремих доменів.
- `mailpit.rs` / `mailpit_commands.rs` — звертається до локального інстансу [Mailpit](https://github.com/axllent/mailpit) для перегляду/читання/видалення/відправлення перехоплених листів.
- `git.rs` / `git_commands.rs` — Git-статус/дії для окремого сайту (ініціалізація, checkout, remote) для контролю версій проєкту.
- `diagnostics.rs` / `diagnose.rs` / `disk_usage.rs` — перевірки стану системи/середовища та звіт про використання диска, показані на сторінці "Стан системи".
- `terminal.rs` / `terminal_commands.rs` / `quick_commands.rs` — PTY-сесії термінала, а також збережені "швидкі команди" та історія команд для кожного сайту.
- `settings.rs` / `settings_commands.rs` — загальні налаштування панелі (мова, оформлення, типові значення проєкту).
- `notifications.rs` / `webhook.rs` — постійне сховище сповіщень у застосунку та опційна пересилка на сумісний зі Slack/Discord webhook, використовується як єдина точка виклику щоразу, коли трапляється подія, важлива для користувача.
- `auto_heal_monitor.rs`, `auto_stop_monitor.rs`, `git_status_monitor.rs`, `tls_expiry_monitor.rs`, `disk_space_monitor.rs`, `backup_scheduler.rs` — опційні фонові потоки (`std::thread::spawn(move || loop { check(&app); sleep(interval) })`), запущені з `bootstrap.rs`, кожен опитує одну умову й звертається до `notifications.rs`, коли вона спрацьовує.
- `project_export.rs` / `project_export_commands.rs` — упаковує сайт (код, базу даних, конфігурацію середовища) у переносний пакет і повторно імпортує його як новий сайт.

## Збірка та інструменти

- **Фронтенд**: Vite 6 + TypeScript + React 19, Tailwind CSS 4. `npm run build` спочатку перевіряє типи, потім збирає; `npm run dev` запускає лише dev-сервер Vite.
- **Бекенд**: стандартний Cargo workspace у `src-tauri/`, зібраний через `tauri-build`; `npm run tauri dev` / `npm run tauri build` запускають повний десктопний застосунок через Tauri CLI (npm-скрипт `tauri` обгортає CLI в `scripts/tauri-clean-env.sh` і передає далі підкоманду — потрібно явно вказати `dev`/`build`).
- **CI** (`.github/workflows/ci.yml`) виконує перевірки фронтенду (Prettier, ESLint, фронтенд-тести, `tsc`, збірка Vite), перевірки Rust (`cargo fmt --check`, `cargo clippy -D warnings`, `cargo test`), а потім збирає Linux-бандли `.deb`/`.rpm`/`.AppImage`.

Дивіться [FEATURES.uk.md](FEATURES.uk.md) для огляду кожної фічі та бекенд-команд, що її реалізують.
